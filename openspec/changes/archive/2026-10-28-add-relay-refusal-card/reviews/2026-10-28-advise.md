1. Pin: the card's source is the beads record (export/show), not `bd blocked`. `status.py` builds Blocked only from `bd blocked --json` `blocked_by`, so an external-only wait never reaches the printer.
2. Pin: the edge `bd ready` honors is a local bead. The `external:<project>:<capability>` id is a reference carried by that bead, not the blocker.
3. Pin: if the record can't be read, say so and name the node. No project from prose, titles, or memory.
4. Pin: Empty prints "no recorded outside wait". It does not fall back to the drilled essay.
5. Pin: the card is additive. It renders. It doesn't decide the refusal, flip a banner, or close a bead.
6. Pin: rows are scoped by action. A row that blocks live-execute is not the cause of a banner-flip refusal.
7. Pin: one renderer feeds the verb reply, `status` Blocked, and `map`, so the three can't drift.
8. Refuse: deriving projects by parsing note or essay text.
9. Refuse: any status or map path that writes beads or banners.
10. Tradeoff: a local stand-in bead per outside wait makes `bd ready` honest. The cost is duplicate state that someone has to close by hand when the other repo ships, plus task/epic type matching for every stand-in.

That is the right call. `bd dep add --help` says external refs "block … until shipped" when `external_projects` is configured. Making the local bead the edge holds up whether or not that config exists, and the delta words it as "not proof", not "never blocks". The epic/gate asymmetry is handled rather than papered over.

I checked one concern myself and it does not hold. Gates are not dropped from a plain export. In a throwaway DB, `bd export` without `--all` kept the `gate` issue and the node's edge to it, even though the help text lists gates under `--all`.

## Pins for act (not verdict blockers; added to tasks.md)

A. **Deferred has no link.** Design says a deferred bead "is not a blocks edge", but the printer "SHALL read dependency edges". Nothing tells it which node a deferred bead belongs to, so the Separate/deferred line can't be found or tested. Name the link: a `related` dep from the node (`bd dep add <node> <deferred> -t related`), and read it from the export. The same-type rule isn't needed for a bead that is not a blocker.
B. **Status when export fails.** If `status` can't read the export, keep the current `waiting on <id>` line. It must name no project. This matches the printer's Failed rule.
C. **Unknown node.** A node id missing from the export must not print `No outside wait recorded`. Treat it as unreadable, or give it its own line. Never as empty.
D. **Missing fields.** An `outside` bead without `project:` or `external:` prints its id and title and marks the field missing. It does not derive a project from the title.
E. **One authority for `external:`.** The `external:` line in the local bead's description is what prints. The node-level `external:` dep, when present, is a mirror only. If they disagree, print the description value.
F. **Off journey wording.** Under a missing-grant, stale-contract, or unaccepted-advise refusal, the pasted card leads. The verb's own reason must follow at once, so the card's `Refused:` header isn't read as the only cause.

Not in scope here, and not flagged: filing api-proxy beads, and teaching `bd ready` about `external:`.
