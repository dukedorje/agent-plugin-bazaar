## Blind take

These ten lines were written to `2026-10-30-blind-take.md` before opening
`design.md` or `tasks.md`, using the Why, living remote-stage spec, and cited
code. They are concerns for the author to answer, not a replacement design.

1. Pin the named store, its access protocol, and its location relative to the session machine before choosing a runner.
2. Pin an explicit distinction between conductor-local sources and session-machine store sources; existing src semantics must remain intact.
3. Pin who provisions and mounts the store; staging must not silently create infrastructure or select another host.
4. Pin the store-relative source and destination resolution rules, including what an unavailable store means.
5. Preserve whole-list validation, declaration order, first-failure stopping, and explicit per-entry delete authority.
6. Preserve the idle check and existing session lock around all staging and prompt submission, with no second harness or Ctrl-C.
7. Bound store access by timeout_sec and map missing sources, launch failures, transport failures, and timeouts to pi-stage-failed without paste.
8. Refuse a success result based only on an existing mount directory when the intended backing store may be absent.
9. Refuse hidden environment-selected sources, implicit destinations, or a new packet shape without matching validation and propagation contracts.
10. Tradeoff: a pre-mounted store keeps the staging runner small, but requires an explicit mount identity and readiness contract outside that runner.

## Comparison and steelman

The author correctly refuses to mistake an unmounted disk for a readable
store. `design.md:8-29` records the negative observation and labels the mount
hypothesis unverified. I have not independently verified the guest observations;
this review did not contact it. `steer.md:8-16,24-28` explicitly chooses spike
before act, boot-time attachment on new guests, and no invented packet field.
Those decisions answer the provisioning concern and justify postponing the
transport choice. Reusing the existing stage hook also preserves a useful
boundary: `spawn.py:602-630` holds and releases the lock around `run_turn`,
and `pi_tmux.py:328-349` stages before either prompt operation.

The strongest case for acceptance is that this is intentionally a guarded
placeholder: it records the right invariant without guessing infrastructure.
That is a sound planning state. It is not yet an implementation contract.
My blind take should not force a mount, new discriminator, or second transport
before evidence selects one. The required amendment is to resolve the gate
and specify the resulting contract, then obtain a fresh review; it is not to
implement my preferred design. The recorded spike remains the appropriate
next investigation before act, under its own authorized scope.

## Findings and required amendments

1. **Blocking: the source and readiness contract is still unknown.**
   `design.md:26-37`, `steer.md:24-28`, and the first task leave the store and
   transport undecided. A builder cannot distinguish the intended backing
   store from a missing mount, choose the execution machine, or specify a
   successful transfer. Complete the recorded spike/steer gate without
   guessing a store. Record the selected identity/protocol, source and
   destination interpretation, readiness evidence, and provisioning boundary.
   If the selected source is a mount, distinguish a mounted backing store
   from its merely existing mountpoint. A `skipped` hypothesis alone does
   not supply these implementation decisions.

2. **Blocking: the eventual declaration needs reconciliation with the living
   contract, not only an added fail-closed paragraph.** The delta currently
   adds one requirement and explicitly defers declaration shape. The living
   `Stage declaration` requires conductor-local `src`, and `Rsync runner`
   applies rsync to every declared entry. `pi_tmux.py:51-56` checks source
   existence on the conductor; `validate_stage` rejects extra keys;
   `run_turn:335-338` normalizes only src/dest/delete. A session-side source
   cannot silently reuse that meaning. After the store is selected, specify
   the compatible declaration and dispatch rule, amend affected requirements
   with complete MODIFIED blocks, and name any schema, validator, normalization,
   and packet-to-spawn propagation changes actually needed. Keep existing
   rsync entries unchanged. Pin success as exit zero and explicitly retain
   timeout_sec, pi-stage-failed, ordering, whole-list validation, delete
   authority, and lock release. Add focused fake/local acceptance for successful
   staging, unavailable store, non-zero/timeout, malformed declarations, and
   legacy/no-stage behavior; inherit existing hook coverage where sufficient.

3. **Required correction: failure means no new prompt write, not necessarily
   an absent prompt file.** Delta `specs/remote-stage/spec.md:15` and the
   proposal's Failed journey require absence. The reusable prompt path can
   already contain a prior turn's file; `pi_tmux.py:341-349` returns on stage
   failure without deleting it. Align the scenario and journey with the
   requirement's actual promise: no write_prompt and no submit for the failed
   turn, with a pre-existing prompt unchanged. Include that initial condition
   in the acceptance case. Do not introduce prompt cleanup merely to satisfy
   the current wording.
